## Project Generation Instructions

When this skill is invoked to generate the React + TS project folder, review this paper-specific
plan **together with** `assets/global-guides/SKILL.md`, its `contract.md` and relevant
`references/` / `scripts/*.md`, `assets/layout-gallery/`, and the React scaffold's
`src/types.ts`. The global contract governs hard constraints, this plan governs paper facts
and per-slide decisions, and the scaffold governs runtime fields. Correct a disagreement in
the plan before coding. Then follow these steps:

### Step 1: Scaffold the project folder

Run `node scaffold.js <outputDir> <packageName> "<titleEn>" "<titleZh>"` from this skill's
directory (scaffold.js sits beside `assets/`). This copies `assets/react-template/` to
`<outputDir>` (the caller's working directory, named `<paper-short-name>_output`) and injects
the paper title into `package.json` and `index.html`, and ensures `public/images/` exists.
Do **not** re-emit the framework files — they are already complete.

Then run `npm install` in `<outputDir>` so the template's TypeScript/esbuild is available to the
syntax gate in Step 4 and to the final validation. Assembly may surface structural errors without
the parser, but final delivery is blocked until the required syntax gate runs successfully.

### Step 2: Create the shared record and isolated packet directories

Under the recorded task-scoped temporary root, create `chapter-work/shared.json` with the final
`meta`, `hero`, and optional `bilibili` objects. Do not put chapters in this file. Create disjoint
packet directories under `chapter-work/packets/<packet-id>/`, using the ownership in the immutable
shared contract. No packet may write into the output project.

### Step 3: Produce chapter and widget packets

Before writing widgets, read this skill's slide-by-slide planning records **and** inspect the staged global guides, `assets/layout-gallery/catalog.md` and `index.html`, and the scaffold's actual types and scene components. Use each page's `layoutRef` as a starting sketch, adjust it for the actual paper, or implement the described `custom` composition. The reference ID is planning metadata only; do not add it to `SceneDef`, `outlines.json` or the app UI. Compare page silhouettes, focal objects and scientific interactions across the deck; give explanation the space it needs instead of scaling every life animation to full body.

Read the relevant `MountainPack`, `MountainMap` or `MountainClimb` functions and CSS in
`assets/layout-gallery/teaching-demo/` to understand direct scene operation and shared-state
calculation/animation. Adapt those behavioral ideas to the paper's own causal specifications;
never copy the demo's theme, facts or components into the output. Implement and exercise both
contrasting states on each core-method page. A number reveal or benchmark chart cannot stand
in for an unimplemented method experiment.

Each packet contains:

```text
<packet-id>/
|-- packet.json
|-- chapters/
|   `-- chapter-N.json
`-- modules/
    `-- <component-id>.tsx
```

`packet.json` has `chapters`, an array of relative chapter JSON paths, and `widgets`, an array of
objects with `componentId`, `exportName`, and relative `file` path. Each chapter JSON matches
`ChapterDef`: keep `kind: "chapter"`, `kind: "module"`, the assigned `chap-N` ID, final Simplified
Chinese copy, and registered component IDs. Every widget exports the exact named React component,
uses Canvas, SVG or DOM as suits its physical scene, owns one dominant operation, and updates feedback plus meaningful values,
output, path, or state.
Every `scenes[]` entry needs its own paper-specific `componentId`;
set `moduleId` when it teaches a
chapter module. The old `focus` scene presets are unsupported. For a conclusion, draw the
theme's outcome or verified paper evidence prominently and integrate one to three brief
judgments into that scene. Never create a text-only three-column recap or a small animation
beside one sentence.

Run disjoint packets concurrently only when safe parallel task execution is available. Otherwise
produce the identical packet files sequentially. Workers read this immutable skill but write only
inside their assigned packet directory; they never edit `tutorial.ts`, `registry.tsx`, `paper.css`,
or another packet.

### Step 4: Assemble shared files once

Run `node assemble-chapter-packets.js <outputDir> <task-temp-root>/chapter-work`. This helper is the
only writer for `src/data/tutorial.ts`, packet widget copies, and `src/modules/registry.tsx`. Fix any
duplicate/missing chapter, module, widget, path, export, or component-registration error it reports.
It also parses `tutorial.ts`, `registry.tsx`, and every copied widget with the project's
TypeScript/esbuild and fails on any syntax error (a common cause is a truncated widget missing its
final brace), so a broken widget cannot be assembled.

Then replace `__METAPHOR_CSS__` inside `src/styles/paper.css` `:root {}` once with the approved
paper-specific color overrides (or remove the placeholder line). Do not let packet workers edit
global CSS.

### Step 5: Apply global rules to this paper plan

Read the staged global `SKILL.md`, `contract.md`, presentation and interaction references,
and validation checklist before implementation. Keep this intermediate document focused on
the paper's evidence, selected everyday theme, and each slide's content and geometry; do not
replace global rules with copied summaries. Use the shared PPT player and its actual
`SceneDef` schema. Author only paper-specific data, styles, widgets and staged media; the
assembler owns shared data and registry writes.

For each slide, implement its planned `layoutRef` or custom sketch and distinct scientific interaction or useful theme episode.
Make its scientific explanation readable at fitted slide size, keep interactive outputs and
feedback synchronized, and use the paper's normal terminology in headings. The cover uses the
official English title and synchronized old/new method animations. If a claim or locator is
unclear, check the validated source cache rather than inventing an answer.

### Step 6: Review and validate the folder

Before validation, review the assembled tutorial for canonical terminology, symbol meanings,
evidence boundaries, chapter transitions, duplicated explanations, theme/color consistency,
interaction coverage, and result coverage. Then run the syntax, structural and build gates and fix
all failures. Also preview cover, every chapter, and optional videos at laptop/desktop and
portrait/landscape mobile sizes, with the TOC both expanded and collapsed. After fonts and
images settle, run `auditSlide()` from `src/lib/slideAudit.ts` in the browser; require an empty
result. Repeat for longest feedback, formula-symbol expansion, and every tab/reveal state.
Inspect screenshots for readability and internal overlap. If browser access is unavailable,
report this gate as incomplete. Static syntax checks alone do not establish slide fit.

```bash
node syntax-check.js <outputDir> --require-parser
node validate-output.js <outputDir>
cd <outputDir> && npm run build
```

`--require-parser` fails when TypeScript/esbuild is not installed, so the final sources cannot pass
by skipping the parse. Confirm:
no leftover `__XXX__` / `__METAPHOR_CSS__` / `TBD` / `TODO` in `src/data/tutorial.ts`,
`src/styles/paper.css`, or `src/modules/*`; core methods have meaningful interactive coverage and declared modules are mounted; every `bvid`
(if any) is real; every `src/**` file parses cleanly; and all gates pass. Deliver only the
`<outputDir>` folder.
